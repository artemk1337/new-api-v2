# Настройки способов оплаты

Разделяй настройки по ответственности и сохраняй существующие способы оплаты:

- `General/Общие` управляет доступным составом способов оплаты и уровнями
  cashback. Здесь должны появляться/скрываться варианты, но не секреты и не
  сетевые реквизиты.
- `PayMethods` — единственный источник истины для доступности метода: quote,
  create, status, webhook и reconciliation endpoints обязаны читать актуальное
  значение из БД, а не устаревший snapshot или legacy-список. Выключенный
  метод нельзя принять через прямой вызов API.
- `Billing/Payment` содержит только безопасные provider-specific параметры:
  receiving addresses, валюту и сеть. Для direct crypto валюта фиксирована как
  `USDT` и должна навязываться server-side (UI control только read-only). Для
  каждой сети используй отдельное поле адреса (`USDT TRON`, `USDT TON`,
  `USDT Solana` и т. п.); для Solana отдельно указывай owner address и точный
  SPL token account, куда отправляется USDT. Поддержаны TRON/TRC20, TON и
  Solana с полным end-to-end контрактом (валидация, watcher, settlement,
  reconciliation и finality). Будущие неподдержанные сети допустимы только как
  staged-конфигурация: показывай их disabled/невыбираемыми и никогда не
  публикуй/не принимай до готовности полного end-to-end контракта.
- `Security/Rate Limit` содержит пользовательские лимиты (включая лимит
  созданий прямых оплат за час), а не настройки метода оплаты.

При изменении UI и API:

1. Проверь persistent-модель `PayMethods`, её сериализацию, миграции SQLite,
   MySQL и PostgreSQL, а также обратную совместимость старого бинарника.
2. Сохраняй visibility direct-only для прямых crypto-методов и не меняй
   legacy-провайдеров или их ключи/маршруты без отдельного требования.
   Фиксированные currency/network/contract/address не принимай из client
   request и не позволяй ими подменить snapshot уже созданного заказа. Для
   каждой поддержанной сети (TRON, TON, Solana) snapshot адреса должен быть
   immutable; staged-адрес будущей сети не может попасть в payable invoice.
3. Все пользовательские строки добавляй через существующий i18n workflow во
   все шесть локалей (`en`, `zh`, `fr`, `ja`, `ru`, `vi`); не оставляй текст,
   доступный только на одном языке.
4. Секреты (API keys, приватные ключи, seed-фразы) не показывай во frontend,
   логах или persistent-настройках, если текущий контракт этого не требует;
   маскируй их при чтении и проверяй авторизацию админа.
5. Добавь детерминированные backend/frontend тесты на сохранение состава,
   cashback, валидацию сети/валюты, direct-only visibility и отсутствие
   регрессий legacy-методов. Проверь `git diff --check` и целевые тесты.

Не смешивай лимит создания оплат на пользователя (окно и значение `0`) с
глобальным rate limit HTTP/API. Не размещай provider-specific поля в General:
адреса/сети/валюта остаются в Billing/Payment, секреты — в backend-хранилище.
